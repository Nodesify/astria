# Paired structural retrieval (schema 3)

Run from the repository root after building the local CLI and native library and installing `js-tiktoken` for `scripts/bench/tokenize.mjs`. Use an isolated Python environment with Graphify installed editable from a clean, explicitly pinned local checkout (`python -m pip install -e /path/to/graphify`). The runner verifies the checkout's full commit and imported module path, and invokes both extraction and queries with that same Python interpreter. It never installs or fetches dependencies.

1. Copy `config.example.json` to a local configuration. Set `python`, `graphify_source`, `graphify_commit`, `astria_cli`, and `astria_native` to your local build and pinned checkout. The example paths describe the saved September 27 run; replace corpus `source` paths with your own local Git clones. Use full 40-character commit pins.
2. Choose a **new** `output` directory. The runner refuses existing output directories, creates separate fresh git archives for each tool, and excludes stored graphs/build caches. Corpus snapshots intentionally use committed files; the candidate Astria binary may contain local changes, recorded in provenance. No graph is reused.
3. `node scripts/bench/paired/run.mjs path/to/config.json`
4. `node scripts/bench/paired/report.mjs path/to/output/results.json`

Paths are relative to the invocation directory. The CLI distribution is copied into the run and paired with the explicitly supplied native binary; both build and query use that binary. CLI dependencies must already exist in the supplied distribution's sibling `node_modules`. Build logs, native/CLI hashes, source status, corpus/golden hashes, complete raw outputs, exact token counts, timings, failures, and per-query metrics are retained. The local Git HEAD describes source provenance, not proof that a binary was built from it: build the supplied artifacts yourself and retain build logs.

## Separate evaluation tracks

- **Frozen v1**: the original 35 self questions plus eight external questions remain unchanged. The example uses these files verbatim. Optional `definitions` sidecars attach symbol diagnostics without editing question text or file goldens. These sidecars cover Click's scoped overrides and Express's response bindings; they are known failure diagnostics, not held-out evidence.
- **Corrected self v2**: `quality/golden/astria-self.v2.jsonl` differs only by adding the authoritative `crates/astria-core/src/languages.rs` target to q06. Select it explicitly with `split: corrected-v2`. Never relabel v1 historical scores or pool both versions.
- **Additional validation v1**: seven independently authored, source-grounded external cases in `*.heldout-v1.jsonl`; the filenames preserve the authored version, while configurations label the split `additional-validation-v1`. They cover a different JS binding, Python overrides, Rust inline-test intent, explicit test and documentation intent, a compound identifier, and a two-file construction flow. They were authored from pinned source before candidate retrieval results were viewed and have now been exercised during validation. Do not describe subsequent runs as untouched held-out confirmation. Reserve new questions for future tuning and evaluation. This small set is not sufficient for general superiority claims.

The report keeps every corpus and split separate. A `definitions` entry identifies a declaration by exact source path and line, with `contains` checked against the fresh corpus before building. `symbol` documents its lexical scope. Ground truth uses one-based lines; Astria zero-based stored/rendered lines are incremented, while Graphify `L` locations stay one-based. Matching a file alone never counts as a symbol hit. Definition rank counts returned NODE records; file rank counts distinct files. Missing definitions and failed queries count as misses. Documentation/test file-only cases intentionally have no definition metric.

Astria additionally records every supported code declaration from SQLite `extraction_cache` and whether its **exact scoped ID** survives in the exported graph. This audit separates missing extraction (grounded presence) from destructive merging (cached identity retention), and retains labels, full IDs, source locations, and every missing ID. It does not infer equivalence from similar labels. Existing retention metrics count unique IDs, so an ID surviving does not prove that every definition has a distinct identity. The additive `duplicate_ids_with_distinct_locations` field lists cached IDs assigned to multiple source locations; inspect these separately for collisions or intentional shared identities. Repeated copies at the same location are not reported as distinct definitions. Run the audit alone with `python scripts/bench/paired/audit-symbols.py /path/to/corpus`.

## Measurement limits

Both tools run structurally without LLM enrichment or embeddings. Serial builds and alternating query order include process startup, with one observation per condition and no filesystem-cache flushing. Budgets are 1,000 and 4,000 o200k_base tokens. The runner counts **raw complete responses** for compliance, then applies identical exact complete-line clipping for retrieval scoring. Clipping does not conceal an over-budget result. Build pipelines differ; build time is practical elapsed time, not an identical-algorithm comparison. Definition-preservation counts are not answer correctness, and file retrieval is not downstream task success. This implementation supplies no new comparative measurements.
