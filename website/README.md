# nodesify-graphify docs site

Docusaurus v3 site deployed to GitHub Pages at
https://nodesify.github.io/nodesify-graphify/ via
`.github/workflows/docs.yml` (builds on every push touching `website/**`
to `main` or `develop`, plus manual `workflow_dispatch`).

## Local development

```bash
cd website
npm install
npm start        # dev server with hot reload
npm run build    # production build (what CI runs)
npm run serve    # serve the production build locally
```

## Documentation structure (Next version)

`website/docs/` follows a Diátaxis-flavored layout:

- `intro.md`, `getting-started.md` — top-level (tutorials)
- `guides/` — task-oriented walkthroughs (wiki & exports, semantic
  enrichment, agent integration, global graph, memory & learning)
- `reference/` — exhaustive lookups (CLI, MCP tools, env vars, language
  support, troubleshooting)
- `explanation/` — architecture and benchmarks

Each folder has a `_category_.json` (label + position); pages order
themselves via `sidebar_position` frontmatter. The sidebar is fully
autogenerated (`sidebars.js`).

**Linking rules:** inside docs, always link *relatively* between pages
(`../guides/global-graph`) — Docusaurus rewrites them per version, so they
keep working in versioned snapshots. Absolute `/docs/...` links from the
landing page, blog, or footer route to the **default version**, which is
the last release (currently 0.8.0, old flat paths) — so use old paths
there; `@docusaurus/plugin-client-redirects` (configured in
`docusaurus.config.js` via `createRedirects`) redirects pre-reorg paths to
their new folder, and keeps doing so after the next version cut.

## Cutting a new docs version

The published site always shows the **latest release** by default
(`lastVersion` in `docusaurus.config.js`). `website/docs/` is the
in-progress "Next" version and carries an unreleased banner.

When a release ships (e.g. v0.9.0):

```bash
cd website
npm run docusaurus docs:version 0.9.0
```

This snapshots `docs/` into `versioned_docs/version-0.9.0/` and adds the
version to `versions.json`. Then update `docusaurus.config.js`:

1. `lastVersion: '0.9.0'` — the new structure becomes the site default
2. add a `'0.9.0': { banner: 'none' }` entry under `versions`
3. update the version-badge source if the shipped version changed (the
   landing-page badge reads `customFields.productVersion`, which points at
   `packages/graphify-cli/package.json`, so it usually needs no edit)

Commit and push — CI redeploys. Old links to pre-reorg paths
(`/docs/cli`, `/docs/benchmarks`, …) keep working via client-side
redirects to the new folders.

## Blog

Release notes live in `blog/` (enabled in the preset config; indexed by
search). A post is plain markdown with `title`/`authors`/`tags`
frontmatter; the filename date controls ordering. Ship a post per release.

## Search

Local build-time search via `@easyops-cn/docusaurus-search-local` — indexes
all docs versions plus the blog at build, no external service. To switch to
Algolia DocSearch (apply at https://docsearch.algolia.com/), remove the
search entry from the `themes` block in `docusaurus.config.js` and add an
`algolia` key to `themeConfig`.

## llms.txt

`docusaurus-plugin-llms` generates `llms.txt` / `llms-full.txt` into the
build output — the whole site as plain markdown for AI agents, which is
rather the point of this project. Verify after a build:
`ls build/llms.txt build/llms-full.txt`.

## Diagrams

Mermaid is enabled (`markdown.mermaid: true` + `@docusaurus/theme-mermaid`).
Use ```` ```mermaid ```` fences in any doc (see
`docs/explanation/architecture.md` for the pipeline diagram).

## Benchmark snapshot

`docs/explanation/benchmarks.md` renders
`src/data/benchmarks-snapshot.json` (via
`src/components/BenchmarkSnapshot`). To refresh it: **Actions → Benchmark
snapshot → Run workflow** — it runs both tools (ours + the original Python
graphify pinned to `91f4d12`) on a fresh runner via
`scripts/bench/run-snapshot.mjs`, commits the updated JSON, and dispatches
this site's deploy. Locally you can run the same with
`node scripts/bench/run-snapshot.mjs` (needs `uv`, and the published CLI).

## Social preview image

`static/img/og-image.png` (1200×630) is referenced by the `og:image` /
`twitter:image` metadata in `docusaurus.config.js` and is also suitable as
the GitHub repo social preview (Settings → General → Social preview).

To regenerate it after a rebrand: open `scripts/og-image.html` in a browser
at a 1200×630 viewport and take a full-viewport screenshot over
`static/img/og-image.png`.
